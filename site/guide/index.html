Domain automation, with the customer keeping ownership

Can Suaka register and manage domains for customers without owning them? Yes. This guide summarizes the research against Porkbun's first-party API documentation and lays out the planned customer wizard.

Short answer

Porkbun's API registers domains directly (POST /api/json/v3/domain/create/{domain}), paid from prepaid account credit, USDC, or a card hold. First registrations over the API are allowed. Requirements and limits: the account's email and phone must be verified first, each API order is capped at $100, and API spending is capped at $100/month by default (the account holder can raise it). Premium names are website-only.

But automation does not require Suaka to own anything. Three things stay separate throughout: the registrant details (who owns the domain), the registrar account (who controls it), and DNS automation (who edits records). DNS can be automated with Suaka holding neither ownership nor the customer's password.

Three ownership models

All three support automation of the full domain lifecycle under the stated grants. They differ in who owns and controls the domain.

1. Customer's own account Recommended

The customer registers and owns the domain in their own Porkbun account. Suaka can manage DNS without handling the customer's password, using either of two official flows:

  • DNS Connect: Suaka signs the record set as a JWT; the customer approves each request on porkbun.com and can undo applied changes within 30 days. It gives Suaka no standing access and requires a one-time client registration with Porkbun review.
  • DNS-scoped API key: the customer hands Suaka's app a key limited to DNS operations through Porkbun's PKCE key-handoff flow. Unlike DNS Connect, this is ongoing, scoped access until the key is revoked.

2. Suaka-owned, then handover

Suaka registers the domain via the API, then pushes it free of charge into the customer's account ("Account Transfer" in the dashboard: pick the username, the customer accepts by email within 72 hours; brand-new accounts need ID verification first). Caveat: there is no public API endpoint for the account-to-account push itself, so the handover step stays manual.

Porkbun's Domain Name Registration Agreement expressly contemplates buying domains on a third party's behalf, with conditions: the customer must accept Porkbun's agreement, Suaka keeps evidence for 3 years, and Suaka must not present itself as a registrar.

3. Suaka subaccounts

Register in Suaka's parent account, then push the domain into a per-customer subaccount with its own login. Suaka retains ownership and transfer control. Subaccounts are an officially documented feature.

The planned customer wizard

For the recommended customer-owned model's basic registration path, the customer handles signup, email and phone verification, payment, domain selection and registration, then approves DNS Connect or grants a DNS-only key. Suaka can automate the invitation and DNS setup. The alternative purchase-scoped registration flow is described below.

  1. Suaka sends the customer a one-time signup invite through the API (POST /account/invite, completion pollable).
  2. The customer creates their account: username, password, a unique primary email, and their own contact details, which become the domain owner details (changeable per domain).
  3. The customer verifies their email and phone (required before registering; verification can be completed via API with codes the customer reads out).
  4. The customer adds payment or credit.
  5. The customer searches for and registers their domain. WHOIS privacy is on automatically.
  6. The customer approves Suaka's DNS Connect request, or grants a DNS-only API key.

Registration itself: two ways. The wizard above is the manual path: the customer buys the domain themselves and no granted authority is needed. The alternative: if the customer grants Suaka's app an API key with purchase scope and keeps the account verified and funded (credit, or a saved card with auto top-up), Suaka's system can register the domain inside the customer's account, so the customer owns it from the first second without doing the checkout. DNS automation is a separate, lighter grant either way.

Testing without real domains

Porkbun offers a free sandbox (pk1_sb_ keys, fake credit, the full API lifecycle, no real actions), including instant no-signup sandbox keys via POST /apikey/request {"sandbox": true}. Integration testing needs no real domains at all.

For real production-shape runs, the lowest-risk officially documented route is subaccounts under the main account.

Multiple independent accounts: unconfirmed. No first-party terms text we found permits or prohibits one person running several independent Porkbun accounts, and none mention same-person testing. The signup page's email rules (unique primary, reusable backup) imply multiple accounts exist, and subaccounts are official, but that is not a settled policy answer. Anti-abuse and promo-abuse rules are a separate question from account count. Treat it as unconfirmed until Porkbun confirms it; sandbox and subaccounts cover testing without relying on it.
